# 문학 단행본 시리즈 개발 업무 대시보드 — 설계 문서 v2

- 작성일: 2026-08-13
- 상태: 검토 중 (v1 [2026-08-12](2026-08-12-series-dashboard-design.md)을 대체)
- 변경 사유: 작품 선정 목록 관리 도구 → **선정·원고·검토·제작·교정·완료 전 과정 관리 도구**로 확장. 작품 식별을 문자열 조합에서 영구 `work_id`로 전환. 홈 화면을 개인 업무 중심으로 재편

## 0. v1에서 달라진 점 요약

| 항목 | v1 | v2 |
|---|---|---|
| 작품 상태 | 단일 `status` (후보/확정/제외) | `selection_status` (선정)와 `production_status` (제작) 분리 |
| 작품별 업무 | 없음 (메모만) | `work_tasks` 테이블 — 담당자·마감·상태를 갖는 체크리스트 |
| 작품 식별 | `work_key` = 작품명+작가 문자열 | `works_registry`의 영구 `work_id` (W000001…) |
| 작품 상세 | 미정 | 오른쪽 상세 패널(drawer) 확정 |
| 홈 화면 | 활동 피드·마감·권 현황 | **내 할 일 · 주의 필요**를 최상단에 추가, 개인화 |
| 마이그레이션 | — | **해당 없음** — 코드·데이터가 없는 그린필드이므로 처음부터 v2 스키마로 구축 |

변경되지 않는 것: 기술 스택(React 19 + Vite + Tailwind 4 + Supabase + GitHub Pages), 사용자 규모(10~15명), 매직 링크 로그인, 전원 전체 편집 + 이력 기록, 파일 업로드+링크 병행, 작품 원본 데이터의 원천은 Google Sheet(대시보드는 읽기 전용), 범위 제외 목록(채팅·댓글·간트·권한 세분화·모바일 앱·AI 없음).

## 1. 목적

편집부(5명)와 편찬위원단(5명, 외부인 포함, 향후 15명 내외)이 함께 사용하는 단행본 시리즈 개발 대시보드. 권별 작품 선정에서 시작해 **작품 선정 → 원고 → 검토 → 제작 → 교정 → 완료**까지의 실무 진행을 한 화면에서 관리한다. 편집자가 데스크톱에서 하루 종일 쓰는 업무 도구를 기준으로 UX를 설계하고, 반응형 웹은 유지한다.

## 2. 아키텍처

```
편집부·위원 (10~15명)
    │  이메일 매직 링크 로그인
    ▼
series-dashboard (React + Vite SPA, GitHub Pages, hash 라우팅)
    ├─ 홈: 내 할 일 | 주의 필요 | 다가오는 마감 | 권별 진행 현황 | 최근 활동
    ├─ 권별 작품 목록: 검색(시트 데이터) → 추가/선정/순서 + 작품 상세 패널(업무 체크리스트)
    ├─ 일정: 시리즈·권별 마감 (캘린더/목록)
    ├─ 자료실: 권별 폴더, 업로드 + 링크
    └─ 연락처: 구성원 명부
    ▼
Supabase (무료 플랜 시작)
    ├─ Auth: 매직 링크 (Supabase Studio에서 초대 — 6.1 참고)
    ├─ Postgres: members, volumes, works_registry, volume_works, work_tasks,
    │            schedules, files, activity_log (+ 트리거)
    ├─ Storage: 업로드 파일 (50MB/건 제한)
    └─ Realtime: volume_works, work_tasks 변경 구독
    ▲
기존 works Google Sheet (게시 CSV) ─ 작품 원본. 읽기 전용, ID 열 없음 (3.2 참고)
```

### 원칙

- 작품 원본 데이터의 원천은 Google Sheet. 대시보드는 읽기만 한다.
- 관계 연결의 기준은 `work_id`, 표시용 정보는 현재 시트 데이터, 로드 실패·원본 변경 대비는 `work_snapshot`.
- 기존 literature-db의 `parseCSV`·`filterWorks`·정규화(`_authorBase`)·검색 UI 패턴을 재사용한다. 중복 구현 금지.
- 데이터 접근 제어는 전부 RLS로 강제한다. 프런트 코드는 공개 저장소에 있어도 안전해야 한다.

## 3. 작품 식별 — works_registry (A안 확정)

### 3.1 구조

시트에는 손대지 않고, Supabase에 작품 레지스트리를 둔다.

```
works_registry
- work_id      text PK  'W000001' 형식 (시퀀스 기반 자동 발급)
- title        text     대표 작품명
- author_base  text     대표 작가 기준명 (literature-db의 _authorBase 규칙과 동일)
- aliases      jsonb    과거 표기 목록 [{title, author_base}, ...]
- snapshot     jsonb    최초 등록 시점의 시트 행 정보 (갈래, 교육과정 등)
- created_by, created_at
```

- 작품이 어느 권에든 **처음 추가되는 순간** 레지스트리에 등록되고 ID가 발급된다. 이미 있으면 기존 ID를 재사용한다.
- `volume_works`, `work_tasks`, 중복 수록 판정, 활동 이력은 모두 `work_id`에만 묶인다. 시트의 표기가 바뀌어도 이 연결은 절대 끊어지지 않는다.

### 3.2 시트 ↔ 레지스트리 매칭의 한계 (정직한 명시)

시트에 ID 열이 없는 이상, "시트 검색 결과 행이 레지스트리의 어느 작품인가"의 판정은 **정규화된 작품명+작가 매칭**을 한 번은 거쳐야 한다. 이 경계에서 시트 표기가 수정되면:

- 권별 목록·업무·이력은 `work_id` 기반이므로 **아무 영향 없음** (스냅숏으로 계속 표시).
- 다만 검색 결과에 붙는 "N권 수록" 중복 뱃지와 시트 최신 정보 연결이 일시적으로 끊길 수 있음.
- 복구: 상세 패널에서 "시트 표기와 다시 연결" 동작으로 별칭(aliases)에 새 표기를 추가하면 이후 매칭이 복원된다. (검색 결과에서 기존 작품에 수동 연결하는 단순한 UI 1개)

매칭 정규화 규칙은 literature-db와 동일한 코드를 사용한다: 작가는 `_authorBase`, 작품명은 공백 정리 후 비교. 「」 등 괄호류 처리도 기존 파서 규칙을 따른다.

### 3.3 알려진 위험

- 같은 작가·같은 작품명이지만 실제로 다른 작품인 경우(무제 시 등) 하나로 합쳐질 수 있다. 발생 빈도가 낮아 MVP에서는 허용하고, 필요 시 DB에서 수동 분리한다. 병합/분리 관리 UI는 만들지 않는다 (YAGNI).
- 작자 미상 고전은 `author_base = "미상"`으로 묶이므로 작품명 충돌 가능성이 상대적으로 높다. 스냅숏의 갈래 정보를 상세 패널에 항상 표시해 사람이 알아챌 수 있게 한다.

## 4. 데이터 모델

### members (구성원)

| 컬럼 | 설명 |
|---|---|
| id | uuid PK (자체 발급). 업무 배정 등 모든 FK는 이 id를 참조 — 로그인 전 구성원에게도 배정 가능해야 하므로 auth ID와 분리 |
| auth_user_id | uuid unique nullable. 첫 로그인 시 이메일 매칭으로 연결 — 6.1 |
| email | 초대 이메일 (연결 전 매칭 키, unique, 소문자 저장) |
| name, affiliation | 이름, 소속 |
| role | `editor` / `committee` (표시용. 권한 차등 없음) |
| assigned_volumes | 담당 권 번호 배열 (표시·기본 필터용. 편집 제한 없음) |
| phone | 연락처 |

### volumes (권)

v1과 동일: number, title(주제명), status(기획/선정중/확정/제작중/완료), editor_id, note.

### volume_works (권별 수록 작품)

| 컬럼 | 설명 |
|---|---|
| id | uuid PK |
| volume_id | volumes FK |
| work_id | works_registry FK. **NOT NULL** — work_id 없이는 등록 불가 |
| work_snapshot | 추가 시점의 작품 정보 jsonb `{title, author, genre, curriculum}` |
| sort_order | 수록 순서 (간격 있는 정수, 예: 10, 20, 30 — 사이 삽입 여지) |
| selection_status | `candidate`(후보) / `hold`(보류) / `confirmed`(확정) / `excluded`(제외) |
| production_status | `not_started`(미착수) / `in_progress`(진행 중) / `review`(검토 중) / `completed`(완료). 기본값 `not_started` |
| note | 선정 메모 |
| created_by, updated_by, created_at, updated_at | 이력 |

- (volume_id, work_id) unique — 같은 권에 같은 작품 중복 등록 방지.
- 선정 상태와 제작 상태는 독립. 단 UI에서 `excluded` 작품의 제작 영역은 흐리게 표시한다 (의미 없는 조합의 혼란 방지).
- `production_status`는 **수동 변경이 기본**이다. 업무 완료율에서 자동 도출하지 않는다 — 업무 등록 없이 진행되는 작품도 있고, 도출 규칙이 실무 판단과 어긋나면 더 불편하기 때문. 대신 모든 업무가 완료되면 상세 패널에 "제작 상태를 '완료'로 변경할까요?" 원클릭 제안을 띄운다 (완료 기준 9 충족).

### work_tasks (작품별 업무)

| 컬럼 | 설명 |
|---|---|
| id | uuid PK |
| volume_work_id | volume_works FK (ON DELETE CASCADE) |
| task_type | 프리셋 키 또는 `custom`. 프리셋: 본문 확보, 저작권 확인, 원고 작성, 해제 작성, 부가 원고, 이미지 확보, 편집 검토, 조판, 교정, 최종 확인 — **코드의 상수 배열**로만 정의해 추가·변경이 쉽게 |
| title | 표시명 (프리셋 선택 시 자동 채움, 수정 가능) |
| assignee_id | members FK, nullable |
| due_date | date, nullable |
| status | `todo` / `in_progress` / `review` / `done` |
| note, sort_order | |
| created_by, updated_by, created_at, updated_at, completed_at | done 전환 시 completed_at 자동 기록 |

- 작품마다 필요한 업무만 추가·삭제한다. 프리셋은 "자주 쓰는 것 빠른 추가" 편의일 뿐 강제가 아니다.
- "확정 시 업무 자동 생성" 같은 템플릿 일괄 생성은 MVP에서 하지 않는다. 다만 프리셋 다중 선택 추가(체크박스로 여러 개 한 번에)는 클릭 수 절약을 위해 제공한다.

### schedules, files

v1과 동일. files에 `volume_work_id` nullable FK만 추가해 두어(컬럼만, UI는 자료실 단계에서) 향후 작품 단위 자료 연결의 자리를 마련한다.

### activity_log

v1 구조 유지 (table_name, record_id, action, diff, actor_id, created_at). 트리거 대상: volumes, volume_works, work_tasks, schedules, files.

- **기록 제외 규칙**: `sort_order`만 바뀐 update는 기록하지 않는다 (드래그 정렬 1회가 수십 건의 피드 스팸을 만드는 것 방지).
- diff에는 변경된 컬럼의 (이전값, 새값)만 저장한다.
- 피드 문구는 프런트에서 생성한다. 예: "김○○님이 3권 「소나기」의 해제 검토를 완료했습니다", "윤○○님이 「별 헤는 밤」의 제작 상태를 '검토 중'으로 변경했습니다". 문구 생성 함수는 순수 함수로 두고 유닛 테스트한다.

## 5. 화면 설계

### 5.1 권별 작품 목록 (핵심 화면)

- 좌: 작품 검색 (literature-db의 검색어·초성·교육과정·갈래 필터 이식). 검색 결과 행에는 work_id 매칭 기반 "N권 수록/후보" 뱃지 표시.
- 우: 선택한 권의 수록 목록. 행 구성:

```
소나기 / 황순원          [확정] [진행 중]  ▓▓▓░░ 4/8   담당 김○○ · D-3
```

  - 배지 2개(선정/제작) + 업무 진행률(done/전체) + 가장 임박한 마감.
  - 위/아래 이동 버튼 + 드래그로 순서 조정.
- 목록 필터: 선정 상태, 제작 상태, 담당자(업무 담당 기준), 마감 임박(7일), 완료 여부. 검색 패널(시트 검색)과는 별도 영역이라 충돌 없음.
- 행 클릭 → **오른쪽 상세 패널** (화면 이동 없음):
  - 작품 정보: 작품명, 작가, 갈래, 교육과정, 다른 권 수록 여부(work_id 기준, **후보/확정 상태 포함** — 권 간 중복 선정은 허용하고 확정 판단 재료로 표시), 저작권 뱃지(4단계에서)
  - 선정: selection_status 변경, 선정 메모
  - 제작: production_status 변경, 진행률, 업무 체크리스트(체크 = done 토글, 담당자·마감일 인라인 편집, 추가·삭제)
  - 자료: **해제 원고 업로드/링크 첨부 + 업로드 여부 표시** (3단계 — files.volume_work_id 사용, 확정 작품의 필수 산출물 추적). 그 외 권별 자료실은 5단계
  - 이력: 이 작품의 최근 activity_log 5건
- 목표 흐름의 클릭 수: 권 선택(1) → 작품 행 클릭(1) → 패널에서 담당자/마감 인라인 수정(1~2) → 체크 완료(1). 저장 버튼 없이 즉시 저장 + 실패 시 토스트·롤백.

### 5.2 홈

```
[내 할 일]                     [주의 필요]
[다가오는 마감]
[권별 진행 현황]
[최근 활동]
```

**내 할 일**: 로그인 사용자에게 배정된 미완료 work_tasks. 우선순위 = ①마감 지남 ②오늘 ③3일 이내 ④7일 이내 ⑤그 외(마감 없음 포함). 항목 클릭 → 해당 작품 상세 패널을 그 자리에서 연다. 완료 처리는 패널에서 한다 (홈 UI 단순 유지).

**주의 필요** (현재 데이터로 계산 가능한 규칙만, 우선순위 순):

| 우선순위 | 규칙 |
|---|---|
| 높음 | 마감이 지났지만 완료되지 않은 업무 |
| 높음 | `confirmed`인데 등록된 업무가 0건인 작품 |
| 중간 | `in_progress` 상태인데 담당자가 없는 업무 |
| 중간 | 마감 7일 이내인데 `todo`인 업무 |
| 중간 | `confirmed` + `not_started`가 14일 이상 지속된 작품 (updated_at 기준) |
| 중간 | `confirmed`인데 해제 원고(작품 연결 파일)가 없는 작품 |
| (4단계) | `confirmed`인데 저작권 상태 미확인 — 작가 단위 데이터라 참고용임을 UI에 명시 |

자료실-작품 연결 기반 규칙(원고 파일 없음 등)은 이번 범위에서 제외한다.

**다가오는 마감**: schedules + work_tasks의 7일 이내 마감 통합 목록.

**권별 진행 현황**: 권별로 확정 수 / 제작 완료·진행·미착수 수 / 진행률. 진행률은 두 가지를 표시 — ①작품 기준(완료 작품/확정 작품) ②업무 기준(done 업무/전체 업무). 막대 1개 + 숫자, 그 이상의 시각화는 하지 않는다.

**개인화**: 담당 권(assigned_volumes)이 있으면 권별 현황에서 담당 권을 먼저 표시. 데이터 접근 자체는 전원 동일.

### 5.3 일정 / 자료실 / 연락처

v1과 동일 (일정: 캘린더+목록, 자료실: 업로드+링크, 연락처: 명부).

## 6. 인증·보안 — 비판적 검토에서 나온 수정 사항

### 6.1 초대 흐름 (v1에서 변경)

v1은 "편집부가 대시보드에서 이메일 초대"라고 썼으나, **사용자 초대(admin API)는 service-role 키가 필요하고 이 키는 정적 프런트엔드에 둘 수 없다.** Edge Function을 만들면 해결되지만 15명 규모에 과하다. 수정:

- **초대는 Supabase Studio에서 수동으로 한다** (편집부 관리자 1명이 Authentication → Invite user). 연 몇 회 발생하는 작업이라 충분하다.
- 초대와 함께 members 행을 등록한다 (대시보드의 연락처 화면에서 이메일 포함 정보 입력 — 이건 일반 테이블 쓰기라 앱에서 가능).
- 첫 로그인 시 트리거가 `auth.users.email = members.email`인 행에 `members.auth_user_id = auth.uid()`를 연결한다. 이렇게 하면 **로그인 전 구성원에게도 업무 배정 가능** (완료 기준 6 충족).
- 미초대 이메일: `signInWithOtp`에 `shouldCreateUser: false`를 사용해 초대된 계정만 로그인 가능.

**별도 관리자 페이지는 만들지 않는다.** 전원 동일 권한이므로 앱 안에서 관리자만 쓰는 화면이 없다 — 권 생성·구성원 명부·업무 관리 전부 일반 화면에서 전원이 할 수 있다. 앱 밖 관리 작업(구성원 초대, 잘못된 데이터의 직접 수정·복구, 백업)은 편집부 관리자 1명이 Supabase Studio(웹 관리 콘솔, 무료 제공)에서 수행하며, 이 절차는 4단계에서 운영 문서로 정리한다.

### 6.2 이메일 발송 한도 (운영 함정)

Supabase 기본 메일러는 무료 플랜에서 시간당 발송 한도가 매우 낮다(시간당 수 건). 매직 링크 전용 로그인에서 이는 실사용 장애가 된다. 대응:

- 세션을 길게 유지해(기본 refresh token 방식) 재로그인 빈도 자체를 낮춘다.
- **커스텀 SMTP를 초기 세팅에 포함한다.** 발신은 Gmail SMTP(앱 비밀번호) 사용 — 별도 도메인·비용 없이 일 500건 한도로 15명 규모에 충분하다. 이것 없이는 10명 동시 온보딩이 안 된다.

### 6.3 무료 플랜 일시정지 (운영 함정)

Supabase 무료 프로젝트는 **7일간 요청이 없으면 자동 일시정지**되고 수동 복구까지 사이트가 죽는다. 방학·휴지기에 실제로 발생할 수 있는 시나리오다. 대응:

- 운영 문서에 명시하고, GitHub Actions로 주 1회 keep-alive 요청 스케줄을 넣는다 (배포 워크플로에 cron 추가, 5분 작업).
- 서비스가 본궤도에 오르면 유료 전환($25/월)을 검토한다. 이 결정은 사용 개시 후로 미룬다.

### 6.4 RLS

- 모든 테이블 RLS 활성화, 기본 거부. 정책: `authenticated` 역할이면서 members에 연결된 사용자만 SELECT/INSERT/UPDATE/DELETE 허용.
- 담당 권에 따른 편집 제한은 두지 않는다 (확정 사항).
- `created_by`/`updated_by`는 클라이언트 입력을 믿지 않고 **트리거에서 `auth.uid()`로 자동 기록**한다.
- Storage 버킷도 동일 원칙 (authenticated + members 연결자만).
- 연락처(외부 위원 전화번호 등 개인정보)가 걸려 있으므로 RLS는 이 프로젝트의 최우선 보안 경계다. 스키마 구축 단계에서 **비로그인/미초대 계정으로 접근이 전부 거부되는지 확인하는 테스트를 필수로 포함**한다.

### 6.5 배포

- GitHub Pages(공개 저장소) + hash 라우팅(`/#/volumes` 형식 — Pages는 서버 리라이트가 없으므로 BrowserRouter 대신 HashRouter). 매직 링크 redirect URL도 hash 경로 기준으로 Supabase에 등록.
- 저장소에는 비밀이 없어야 한다: anon key는 공개 전제(RLS가 방어선), service-role 키는 어디에도 커밋 금지.

## 7. Realtime

- 구독 대상: `volume_works`, `work_tasks` (권 화면·상세 패널·홈이 공유하는 스토어에 반영 → 진행률, 내 할 일, 주의 필요, 권별 현황이 함께 갱신).
- schedules·files·연락처는 조회 시 로드로 충분 (실시간 불필요, 구독 수 절약).
- 끊김 시 자동 재연결 + 재연결 시 전체 재조회. 낙관적 업데이트 실패 시 토스트 + 롤백.
- 동시 편집은 last-write-wins + 이력 복원 (10명 규모에서 충분, v1 유지).

## 8. 오류 처리

v1 유지 + 추가:

- 시트 매칭 실패 작품은 스냅숏으로 표시하고 "시트 연결 끊김" 아이콘 표시 (3.2의 재연결 동작 진입점).
- D-day 계산은 KST 자정 기준 date-only 비교로 통일 (서버 UTC 타임스탬프와 혼동 금지).

## 9. 테스트

기존 literature-db 테스트는 그 프로젝트에 그대로 둔다. 대시보드에 새로 추가:

**순수 함수 유닛 테스트** — work_id 매칭(정규화·별칭 포함), 중복 수록 판정, 작품별/권별 진행률 계산, D-day 계산(KST), 내 할 일 우선순위 정렬, 주의 필요 규칙 판정, 활동 피드 문구 생성, sort_order 재배치 계산.

**컴포넌트 테스트** (Supabase 목킹) — 상세 패널 열기, 업무 추가/삭제, 담당자 지정, 마감일 설정, 업무 완료 토글, 선정 상태 변경, 제작 상태 변경(+전체 완료 시 제안 표시), 내 할 일/주의 필요 렌더링.

**수동 점검 체크리스트** — 2개 브라우저 실시간 동기화, 미초대 계정 로그인 거부, RLS(비로그인 API 접근 거부), 매직 링크 수신, 50MB 초과 업로드 거부.

## 10. 개발 단계

| 단계 | 내용 |
|---|---|
| 0 | 본 설계 문서 확정 |
| 1 | 프로젝트 세팅(Vite/React/Tailwind/Vitest), Supabase 프로젝트 생성 + 스키마·트리거·RLS SQL, 커스텀 SMTP, 매직 링크 로그인 + 첫 로그인 연결, 배포 파이프라인(keep-alive 포함) |
| 2 | 권 관리 + 권별 작품 목록(검색 이식, 추가/선정/순서) + works_registry + 상세 패널 + work_tasks + Realtime |
| 3 | 홈(내 할 일, 주의 필요, 마감, 권별 현황, 활동 피드) + 작품 해제 원고 업로드·업로드 여부 표시 (Storage 버킷 이 단계에서 생성) |
| 4 | 일정, 연락처(초대 운영 절차 문서 포함) |
| 5 | 자료실(업로드+링크), 엑셀 내보내기, 저작권 뱃지, (선택) literature-db 수록 현황 페이지 |

각 단계 완료 시 배포하고 실사용 피드백을 받는다. 완료 판정은 아래 시나리오로 한다.

## 11. 완료 기준 시나리오

1. 작품을 권에 추가하면 `후보 / 미착수`로 표시된다 (works_registry에 ID 자동 발급).
2. 선정 상태를 `확정`으로 변경할 수 있다.
3. 작품별 제작 업무를 프리셋에서 여러 개 한 번에 등록할 수 있다.
4. 각 업무에 담당자와 마감일을 지정할 수 있다 (아직 로그인한 적 없는 구성원 포함).
5. 담당자가 로그인하면 홈 '내 할 일'에 우선순위 순으로 나타난다.
6. 마감을 넘기면 '주의 필요'에 자동 표시된다.
7. 업무를 완료하면 작품 진행률과 권별 현황이 즉시 갱신된다.
8. 모든 업무 완료 시 제작 상태를 원클릭으로 `완료` 처리할 수 있다.
9. 다른 사용자 화면(목록·패널·홈)에 변경이 실시간 반영된다.
10. 동일 작품 판정이 표기 차이와 무관하게 work_id 기준으로 동작한다.
11. 미초대 계정은 로그인과 데이터 접근이 모두 거부된다.

## 12. 범위 제외 (하지 않는 것)

v1 목록 유지: 채팅, 댓글, 복잡한 권한 체계, 담당 권별 편집 제한, 모바일 앱, 간트 차트, 복잡한 PM 기능, AI 기능. 추가: 업무 템플릿 일괄 자동 생성, 작품 병합/분리 관리 UI, production_status 자동 도출, 자료-업무 연동 규칙.

## 13. 운영 비용과 용량 (제약: 무료 운영, 15명 동시 사용)

모든 구성 요소가 0원이며, 15명 동시 사용은 무료 한도의 여유 범위 안이다.

| 구성 요소 | 요금 | 무료 한도 | 15명 규모 예상 사용량 |
|---|---|---|---|
| GitHub Pages | 0원 | 대역폭 100GB/월 | 정적 SPA, 수 GB 미만 |
| Supabase DB | 0원 | 500MB | 작품 선정·업무·이력 수만 행 = 수십 MB |
| Supabase Realtime | 0원 | 동시 접속 200 | 최대 15 |
| Supabase Auth | 0원 | MAU 50,000 | 15 |
| Supabase Storage | 0원 | 1GB (50MB/건) | 초과분은 링크 첨부로 흡수 (확정 사항) |
| Gmail SMTP | 0원 | 일 500건 | 로그인 메일 하루 수 건 |
| works 데이터 | 0원 | 기존 구글 시트 게시 CSV 그대로 | — |

성능 관점: 15명 동시 편집은 Supabase 무료 플랜 기준으로도 소규모다. 병목 후보는 시트 CSV(1만 행) 로드뿐인데, 이미 literature-db 사이트가 같은 데이터를 문제없이 다루고 있고 대시보드는 최초 1회 로드 후 메모리에서 검색한다.

복잡도 관점: 서버·빌드 백엔드 없이 **정적 사이트 1개 + Supabase 프로젝트 1개**가 전부다. 운영 중 사람이 해야 하는 일은 ①새 구성원 초대(Studio에서 클릭, 연 몇 회) ②시트 관리(기존과 동일)뿐이다. keep-alive와 SMTP는 최초 세팅 때 한 번만 만지면 된다.

## 14. 미해결/보류 결정

- 유료 플랜 전환: 원칙적으로 하지 않는다. 저장 용량이 1GB에 근접하면 링크 첨부 위주로 운영해 무료를 유지한다.
- literature-db 사이트에 수록 현황 공개 페이지를 만들지, 공개 범위는 어떻게 할지: 5단계 도달 시 결정.
